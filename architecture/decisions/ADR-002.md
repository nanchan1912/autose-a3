# ADR-002: Ordinary Python code controls the workflow (fixed state machine)

Status: Accepted
Date: 2026-11-24
Decision: D2 (Control flow)

## Context

The stages run in a fixed order, but work sometimes has to go back: failing tests should return to
implementation, repeated failures to design, and review findings to whichever stage needs fixing.
Something has to decide when to retry, when to go back and when to stop.

## Decision

Ordinary Python code (`workflow/autose/pipeline.py`) controls the workflow as a fixed state machine.
Agents produce artifacts; the code decides every transition:

- spec or design check fails: retry the same stage once with the check's feedback, then stop;
- build or tests fail: back to the implementer (at most 3 attempts per design), then back to design
  once, then stop;
- missing or broken tests: back to the tester once;
- reviewer requests changes: a new round resumes at the stage the findings point to (design,
  implement or test), at most 2 rework rounds.

Stages 1-5 run in one Actions job; the review rounds are unrolled as separate jobs
(`autose.yml`: round0 -> round1 -> round2, each the reusable `autose-round.yml`).

## Alternatives considered

- **An AI manager (planner agent) that decides what to do next.** Rejected: it could make
  inconsistent decisions, waste API calls or get stuck in loops.

## Consequences

- Execution order, retry limits and stage transitions are predictable, which makes the workflow
  easier to debug, reproduce and test (the transitions have offline unit tests).
- The loop-back rules are fixed in code; a situation they do not foresee ends in a stop with an
  explanation rather than a creative recovery.
- The review loop is visible in the Actions run graph as separate rounds.
