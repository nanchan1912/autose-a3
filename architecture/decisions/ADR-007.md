# ADR-007: Stage checks are programmatic; the review verdict is computed from findings

Status: Accepted
Date: 2026-11-24
Decision: D7 (Checks)

## Context

Each stage may only hand over once its check passes. The check could be done by an LLM judge, by
code, or by a mix.

## Decision

Every stage check is code (`workflow/autose/checks.py`):

| Stage | Check |
|---|---|
| 1 | every acceptance criterion has given/when/then, an exact observable expected result, no vague words, and is not based on an assumption; or the spec is BLOCKED and asks questions |
| 2 | every planned file exists (or is marked new), every named function/class exists (or is marked new), only allowed paths, every criterion has a planned test |
| 3 | package installs, compiles, imports and converts a document; no new flake8 findings; diff not empty and under 800 lines |
| 4 | full test suite passes and every criterion has a passing test named after it |
| 5 | the PR is open at the tested commit and CI (`ci.yml`) is green |
| 6 | the reviewer agent reports findings; code decides: request changes if any blocking/major finding, or the suite fails, tests were deleted or protected paths changed |

## Alternatives considered

- **An LLM judge deciding whether each stage's work is acceptable.** Rejected as the sole basis for
  acceptance.

## Consequences

- Conditions such as whether required files exist, criteria are concrete, the code builds and tests
  pass can be checked objectively, which makes the workflow more reproducible.
- Subjective AI judgment is never the sole basis for accepting an implementation.
- Code checks cannot judge whether the change actually does what the issue meant; that is left to
  the hidden tests and the independent reviewer.
